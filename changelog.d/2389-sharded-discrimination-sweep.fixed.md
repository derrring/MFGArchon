The weekly test-discrimination sweep runs as five parallel shards, and its killer-set check compares against the committed matrix again (#2389).

- **The single job no longer fit.** Run 34828814112 took 294 of its 300 minutes and the next run was cancelled at the limit, after which the failure notice blamed discrimination. `scripts/test_discrimination.py --shard K/N` runs every N-th mutation starting at K. The N slices partition the mutation list for any N, so a mutation added later belongs to exactly one shard without being assigned. The workflow runs five shards with a 180-minute limit each. `--check-baseline` over a subset (`--shard` or `--only`) compares that subset, and still reports a mutation the code no longer declares. `--write-baseline` refuses `--shard`, and `--only` refuses a name that is not a mutation.
- **The killer-set half of the check was comparing each run with itself.** The workflow passes `--json` the same path `--check-baseline` reads its killer sets from, and the reference was read after the write. Since #2349 (2026-09-19) a test that stopped killing a mutation while another took its place, the case a count cannot see (#1901), could not fail the weekly run. The defect stayed latent: the one scheduled run since then timed out before comparing anything, so it produced no false green. The reference is now read before the sweep. `test_the_killer_reference_is_the_committed_matrix_not_this_runs_output` exits 0 on the old code and 1 on the new. A missing matrix is now refused before any mutation runs, not after.
- **The failure notice says when the sweep did not finish.** It lists each shard's own conclusion, read from the run's job list, rather than the aggregate result, whose treatment of a matrix with both a failed and a cancelled leg is not documented. A cancelled shard has no verdict for its mutations, and the notice says so instead of listing discrimination causes. The issue is closed only by a green run on `main`, not by a dispatch on a branch.
