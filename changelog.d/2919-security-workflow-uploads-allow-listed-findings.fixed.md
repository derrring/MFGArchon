- **The security workflow uploads only allow-listed findings** (Issue #2919). Each scan job in `.github/workflows/security.yml` uploads one file, `<job>-findings.json`, which the new `.github/scripts/security_findings.py` writes. Each finding there holds only its tool, rule, file, line, commit, severity, confidence, package, version, advisory, license and status. A tool's report, stdout and stderr stay on the runner. TruffleHog runs without verification or its update check, detect-secrets without verification, Semgrep with metrics and its version check off and the `p/python` rule pack in place of `auto`, which needs metrics, Trivy without telemetry, its version check or its dependency lookups (`--offline-scan`), and Safety without its optional telemetry or its upload of results.
- **The summary job reads the scan jobs' results, and says when it could not.** `generate_security_report.py` looked for each scan report by its bare name in the working directory, while download-artifact puts several artifacts in a directory each, so it read none. `check_critical_issues.py` looked for four of its six inputs under names no job uploads, and for a fifth at the top level rather than in its artifact's directory. The five findings files now download into one directory (`merge-multiple`; their names are unique), and `security_findings.py collect` writes `security-findings.json` from them alone, which `generate_security_report.py` and `check_critical_issues.py` read. A job whose findings file is missing, or that has a tool whose report is missing, unreadable or of the wrong shape, or says the tool did not finish or scanned nothing, makes the overall status `INCOMPLETE` and fails the summary job, where it had read as a pass. TruffleHog, detect-secrets and Semgrep, which can leave a well-formed report without finishing, keep it only when they exit as a finished scan; a hadolint report that names a Dockerfile it could not parse (`DL1000`) counts as unfinished. Where a tool's report says how many files or packages it scanned and how many it could not, the findings file carries both counts; a tool that scanned none counts as unfinished, and the summary shows each tool's status, findings and counts. The overall status is `INCOMPLETE` when a job is incomplete, else the highest severity the dependency, static and secrets jobs found, with a finding whose tool gives no severity (`UNKNOWN`) ranked below high and above medium, else `PASS`. `security-findings.json` now holds the summary and, for each job, its tools' statuses, its counts and its allow-listed findings.
- **The critical-issues thresholds apply to what the scans found.** They read the dependency findings, the static findings, detect-secrets and TruffleHog, Trivy's vulnerabilities and hadolint, the license findings, and `custom_security_checks.py`. `check_critical_issues.py` has no threshold on the custom secrets scan or the container configuration check, whose own steps fail their jobs on a high-severity finding. Its "verified secrets" arm is gone, since TruffleHog no longer verifies. Semgrep's confidence now comes from each rule's metadata. A license is non-compliant when `license_compliance_check.py` puts it in `review_required` or `prohibited`. Safety's report is written: the workflow had passed `--json` with `--output safety-report.json`, which Safety refuses.
- **The scanners' own reports.** `custom_secrets_scan.py` finds a private-key header with nothing between `BEGIN` and `PRIVATE`. `custom_security_checks.py` and `container_security_check.py` record a finding's file and line, and no longer the source or Dockerfile line there; a file `container_security_check.py` cannot read is named with its exception's class. `parse_security_results.py` is gone: its readers are in `security_findings.py`, and four files it wrote over other scripts' files of the same names are no longer overwritten. The separate `pip-licenses` step is gone with it; `license_compliance_check.py` runs pip-licenses itself.
- **One workflow runs the security scanners.** `ci.yml`'s `security-scan` job ran bandit, Safety and pip-audit on the same triggers as `security.yml` and uploaded their reports whole as the `security-reports` artifact. It is deleted, with the `run_security_scan` input of `ci.yml`'s manual trigger, whose only reader it was.
