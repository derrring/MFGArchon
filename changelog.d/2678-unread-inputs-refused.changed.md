- **Breaking: an input no solve reads is refused when the problem is built** (Issue #2678). Each was accepted and changed the default solve by 0.0 in `U` and in `M`, with nothing said. Refused now: `Model(drift_field=)`; `MFGProblem(drift=)`, in both forms; `MFGProblem(constraints=)`, in both forms; `state_penalty_scale` other than 1.0 with no `state_penalty`; `suppress_warnings=True` on a geometry or a network, where no feasibility check runs (it stays on a grid the library builds itself, from `spatial_bounds=` or the default domain); `spatial_discretization=` anywhere but beside `spatial_bounds=`; and `lambda_=` on a grid built from `spatial_bounds=` or on the default domain, which keep it nowhere. The refusal of a drift names what to do instead: a callable to `solve_fp_system(drift_field=)` on `FPFDMSolver` or `FPParticleSolver`, or to `FixedPointIterator(drift_field=)` over `FPFDMSolver`. Each replaces the drift the Hamiltonian gives, and reads the callable by position as `(t, x, m)` (#2864). An array means different things by solver, and a number has no route. A `Model` now needs a Hamiltonian or a Lagrangian: one with only a `drift_field` built, and then raised at `MFGProblem`.
- **Breaking: `hamiltonian=` is no longer a parameter of `MFGProblem`** (Issue #2563). Beside `components=` it was read by nothing, so the components' Hamiltonian was solved with nothing said; alone it raised, for a missing `m_initial` or a raw callable, so it built no problem. It now raises wherever it is passed, naming `Model(hamiltonian=)` and `MFGComponents(hamiltonian=)`: beside `components=` whatever its value, `None` included; alone; beside a `Model`; and on a subclass that overrides `_initialize_functions`, the one route that used to build with it, which no class in this repository takes.
- **Breaking: `obstacles=` is no longer a parameter of `MFGProblem`, and `problem.obstacles` and `problem.has_obstacles` are removed** (Issue #2678). No solver read them: on a scheme that ran, `sl_linear`, a problem with obstacles gave the same solve as one without, and particles entered the region as if nothing had been passed. All it did was take `fdm` off the problem's compatible solvers, so the default solve refused and listed `gfdm`, which is withdrawn, as the alternative. It now raises wherever it is passed, naming `FPParticleSolver(implicit_domain=DifferenceDomain(...))`, which holds the density out of the region and does not cover the value function. A problem pickled before this change still solves, and raises when it is rebuilt, since its record holds the keyword.
- **`problem.drift_field` and `MFGProblem.get_drift_coefficient_field` are removed, and `has_state_dependent_coefficients` reads only the volatility** (Issue #2678). No solver read any of them.
