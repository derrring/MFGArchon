Single-source ratchet (`scripts/check_single_source.py`), wired into `./scripts/local_ci.sh` and the GitHub PR-check tier. CLAUDE.md names three quantities that must have exactly one owner — `diffusion_from_volatility`, `fp_drift_coefficient`, and since #1894 `hjb_residual_norm` — and nothing measured whether the restatements were growing. The registry records four quantities with their current site counts (36 / 1 / 5 / 12) and fails in both directions: growth is a regression, shrink is progress that must be recorded with `--write-baseline`.

Three design points, each from a measured failure rather than from principle:

- **The sentinel is a live site inside a named `def`, not a stored literal and not merely a file.** A broken pattern returns 0 hits and 0 hits reads exactly like clean code. The first version stored a literal string the pattern had to match, which proves only that the pattern intersects one hardcoded string — never that it still describes the tree. A second review then showed a file-level anchor is still too weak: entry 1's only match in `pde_coefficients.py` sat in `diffusion_from_volatility_torch`, not in the `diffusion_from_volatility` its `owner` field names, whose body computes on a local `arr` no sigma-anchored pattern can see. The sentinel was propped up by a duplicate, and consolidating that duplicate would have bricked the entry. `sentinel_symbol` names the `def` whose body must hold the match, which forced that divergence into the registry instead of leaving it in prose. It closes **total** drift, where the anchor moves with everything else; partial drift still lowers the count and can still be recorded, loudly, via exit 1. Measured: the `D = sigma^2/2` entry had four alternatives of which three were structurally unreachable, because `ruff format` (gated at `local_ci.sh:214`) hugs `**` and no file under `mfgarchon/` can contain `sigma ** 2`. It reported 6 sites where the widened pattern now matches 36, and respelling the counted six to the ruff-canonical form — deleting nothing — dropped the count to 0, printed SHRANK, and offered `--write-baseline` as the remedy. **36 is what the pattern matches, not a census of sites computing `D`** — no regex can be that, and source held in string templates is invisible by construction (`code_generation.py:400` emits `0.5 * sigma**2` into every generated FP solver; the registry note says so).
- **Comments, string literals and f-string bodies are blanked via `tokenize`.** `check_fail_fast.py` records the same trap from its regex era: 40 of 164 `hasattr` "calls" were docstring mentions. On Python 3.12+ f-strings tokenize as `FSTRING_MIDDLE` rather than `STRING`, so blanking only `tokenize.STRING` counted a log message in `pde_coefficients.py:330` as a site.
- **Instrument failure exits 2, distinct from exit 1 "the count changed".** A checker that cannot measure must not return a verdict about the code.

`alg/neural` and `alg/reinforcement` are excluded per the frozen-area rule; all four entries measure 0 there today, so the exclusion changes no current count.
