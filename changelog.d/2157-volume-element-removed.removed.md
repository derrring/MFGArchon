- **`TensorProductGrid.volume_element()` is removed** (Issue #2157). It answered "what volume does node *i* own" and disagreed with `quadrature_weights()`, which has owned that question since #2145. The disagreement was exactly at the walls: on the graded grid `[0, 0.1, 0.3, 0.6, 1.0]` it returned `0.1` and `0.4` at the two end nodes where the quadrature weights are `0.05` and `0.2`, and it agreed to the last digit everywhere in between. So it was the trapezoid rule with each end node counting a half-cell that lies **outside** the declared domain: `sum(volume_element(i)) == 1.25` on an interval of length `1.0`, while `sum(quadrature_weights()) == 1.0` exactly. A caller measuring mass with it was integrating over a domain one cell longer than `get_bounds()` reports -- the same defect #2145 found in `FPFVMSolver`, where it cost an order of accuracy. Neither method said the other existed. It has no meaning the surviving API lacks: the uniform branch is `prod(get_grid_spacing())` and the non-uniform branch is `quadrature_weights()` with the two walls doubled, so this is a deletion rather than a rename. Live callers routed to `integrate()`: the mass gate in `fixed_point_iterator` (see the companion entry), three 2-D application demos, and `docs/user/multidimensional_mfg_guide.md`. Measured on the demos' own configurations, the density they believed had mass `1.0` in fact had `0.98904` (traffic, 51x51), `0.99707` (portfolio, 41x31) and `0.99648` (epidemic, 51x51); their end-of-run "Mass conservation:" line printed the counting integral, which on a fully mixed density reads `(N/(N-1))**d` -- `1.0404` for a solve that conserved mass perfectly. The 21% figure in the issue is the same defect on an 11-point grid and overstates these three.
