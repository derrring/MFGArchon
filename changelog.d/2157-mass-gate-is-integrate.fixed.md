- **The coupled solver's mass gate asked a different question from the one it answered** (Issue #2157). `FixedPointIterator` decided whether `SolverResult.mass_conservation_error` was measurable by calling `geometry.volume_element()`, then measured with `geometry.integrate()`. Only `TensorProductGrid` had either -- of 163 geometry classes it is the only one with any of `volume_element` / `integrate` / `quadrature_weights` -- so the gate was a spelling of "is this a `TensorProductGrid`" that would have refused any future geometry able to integrate, while `MFGProblem` had gated on `integrate` all along. It now asks what its own comment always claimed. Two things went with it. The `np.sum(M, axis=spatial)` fallback behind the gate is deleted: reaching it required a geometry with a volume element and no integral, which no class in the package has, and it was the counting measure #2145 removed everywhere else. The private `_MassNotMeasurableError` sentinel is deleted: it existed only because the deliberate non-positive-mass `raise ValueError` sat inside the same `try` as the measurement, so a plain `except ValueError` would have swallowed a fail-loud; the `try` is now narrowed to the `integrate` call alone and the raise lives outside it, so structure carries the distinction instead of a class relationship. The pin is no longer a class-hierarchy assertion but a real solve with `integrate` patched to refuse (reports `None`, does not raise) and patched to report zero mass (raises, from outside the try), with a control asserting the unpatched fixture reports a number. Removing `volume_element` also makes the gate self-pinning: `TensorProductGrid` is now the "integrate but no volume_element" case, so restoring the old gate turns every coupled solve's mass error to `None` and reddens four tests.
