- **The deprecation removal rule had three in-tree statements that disagreed; they now agree with the code** (Issue #2366).
  - **User ruling:** a deprecated symbol may be removed once **3 minor versions or 6 months** have elapsed, **whichever comes first** — which is what `_removable_by_policy` already executes. The code does not change; the statements align to it.
  - **What disagreed.** `AGENTS.md` clause (4) carried a bare "OR", which now says **whichever comes first** explicitly. `mfgarchon/utils/deprecation.py:45` said *"whichever is longer"*, contradicting `_removable_by_policy`'s own docstring and code, which say *"either suffices"*. `docs/user/LEGACY_PARAMETERS.md` published a **6-12 month** window that matched neither, live and unmarked, in the document users read.
  - **The drift is a three-step compression, each step faithful to the one before.** `a6569f57`'s policy file stated *"3 minor versions OR 6 months (whichever is longer)"*; the `AGENTS.md` clause dropped the qualifier to a bare OR; the code implemented the bare OR as *"either suffices, per the CLAUDE.md policy"*. No step invented anything — each read its predecessor correctly and lost one distinction.
  - **The ruling supersedes that original**, and the practical reason is measured: **zero** call sites record `deprecated_on` (control: 47 `since=` sites), so the six-month arm is unreachable and the executed rule today is "3 minor versions" under either reading. Adopting *"whichever is longer"* would have required backfilling a date onto every live deprecation — a migration, not a wording fix.
  - **#616 does not decide it.** Its failure was a redirect whose behaviour differed from what it replaced, which is clause (1) and the equivalence-test clause — not a premature removal. The post-mortem is silent on *longer* versus *either*.
  - Whether to start recording `deprecated_on` is **not** decided here; the rule works without it.
