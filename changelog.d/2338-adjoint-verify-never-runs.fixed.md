- **`BlockIterator(adjoint_verify=True)` now compares two operators or refuses; it never silently passes** (Issue #2338).
  - **What was wrong:** both the per-step check and `_generate_adjoint_report` asked the FP solver for a `_build_advection_matrix`, a name that exists only on `HJBFDMSolver`. `getattr` returned `None` for every FP solver, so both skipped silently for every configuration, the default FDM pair included. A diagnostic that is present and never runs reads as "adjoint verified" to whoever enabled it. The report path carried a second defect: it passed `A_fp_ind.T` into `diagnose_adjoint_error`, which transposes its other argument, so the two transposes cancelled and it diagnosed `A_fp == A_hjb` rather than the adjoint relation it reports on.
  - **What it compares now:** the FP solver's own advection operator against `build_linearized_operator`, the exact Jacobian — the pairing the adjoint claim (#580, #622, #707) is actually about. Measured at `5d232f62` on a 41-point no-flux fixture, over the interior window: relative error 1.1e-16 under `engquist_osher` against 3.0e-02 under `rouy_tourin` (absolute max|A_fp − J^T| 2.8e-14 against 18.5), either side of the 1e-10 tolerance the check already used. So it now separates the defect #2313 fixed from the pairing that holds. The velocity-mode `build_advection_matrix` the old code reached for is not that pairing and no tolerance would have separated anything there: its relative error against the FP operator is 9.991e-01 under `engquist_osher` and 9.996e-01 under `rouy_tourin`, i.e. it disagrees just as much on correct code.
  - **New:** `FPFDMSolver.build_advection_operator(U, time=..., coupling_coefficient=...)` returns this solver's own advection block, assembled by the same `_INTERIOR_HANDLERS[advection_scheme]` stencil `solve_timestep_full_nd` uses — one owner, no arithmetic restated — with `dt → ∞` so the `1/dt` diagonal drops out and `σ = 0` so the diffusion block does. It fills the rows that scheme dispatches through its interior stencil: strictly interior nodes, and a periodic wall, which dispatches the same way.
  - **Window:** strictly interior rows and columns. `build_linearized_operator` zeroes its wall rows by design (#1564), so a wall row carries no claim on the HJB side and comparing it would report that design as a defect — 94.6 in 1-D and 60.4 in 2-D, for every preset. Choosing the window by which rows happen to be non-zero was measured to be worse: it also drops the interior rows where the Jacobian's row vanishes (3 of 39 on that fixture) while the FP operator has entries up to 62.7 there, which is exactly where a disagreement would hide.
  - **Two refusals, replacing two silences.** `adjoint_verify=True` with an FP solver that supplies no operator now raises `NotImplementedError` naming the solver (`WeakFormFPSolver` is the in-tree case: it satisfies the strict-adjoint protocol and assembles no advection operator). `adjoint_verify=True` with `adjoint_mode="off"` — the default mode — now raises `ValueError`: no adjoint coupling is built in that mode, so there is nothing about the run to verify.
  - **Reporting:** `metadata` gains `adjoint_rows_compared` and `adjoint_max_rel_error`. Without the first, a run that skipped every comparison is indistinguishable from one that made them all and found nothing, which is the state this issue reports and what a `adjoint_mismatch_count` of 0 looked like.
