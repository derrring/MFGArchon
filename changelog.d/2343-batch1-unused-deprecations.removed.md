- **Seven deprecated symbols removed** (Issue #2343, batch 1).
  - `_deprecated_xp_zeros` (v0.17.0, `backends.compat`), `_compute_upwind_advection` (v0.18.0, `fp_solvers.fp_fdm_advection`), the `tensor_volatility_field` parameter of `HJBFDMSolver.solve_hjb_system` (v0.18.7), and the aliases `MFGDriftField` -> `DriftField` (v0.17.1), `FPSLAdjointSolver` -> `FPSLSolver` (v0.17.6), `GradientComponentOperator` -> `PartialDerivOperator` (v0.18.0), `HJBWenoSolver` -> `HJBWENOSolver` (v0.20.5).
  - **Removed ahead of their published targets, under the maintainer's waiver** (AGENTS.md § *Solo Maintainer's Protocol* is self-enforced). `docs/user/DEPRECATION_MODERNIZATION_GUIDE.md` published `remove by v0.25.0` for the first three and `remove by v1.0.0` for the four aliases, against `0.22.0.dev0`. The ruling on #2343 is that pre-1.0 the redundant path goes rather than being preserved. The guide is regenerated from the code by `scripts/generate_deprecation_guide.py`, so its total moved 59 -> 51 — eight entries, because removing `FPSLAdjointSolver` also removed the `drift_field` row it inherited from `FPSLSolver`.
  - **Two of the nine named in the issue were NOT removed, because neither can go alone.** `volatility_matrix` and `tensor_diffusion_field` are one rename with two old spellings — same version, same replacement, same function, stacked as adjacent `@deprecated_parameter` decorators on `FPFDMSolver.solve_fp_system` — and the second had 37 references across 7 files at `456d09c3` excluding `CHANGELOG.md` and `changelog.d/` (40 over 9 counting those), so the pair moves to family 6 rather than half of it moving now. `damping_factor_M` is one name over four surfaces (`BlockIterator.__init__`, `BlockIterator`'s property, `FixedPointIterator`'s own entry, and `PicardConfig.LEGACY_FIELD_ALIASES`) and its sibling `damping_factor` is scheduled for family 4; removing one would leave the same constructor accepting the legacy spelling for U but not for M.

- **Two defects the removals exposed** (Issue #2343).
  - **`test_diagonal_tensor_callable` was passing on the deprecation warning, not on the solver.** It selected warnings containing `"callable"`, and the only one carrying that word was the `DeprecationWarning` for `tensor_volatility_field`, whose replacement text reads *"volatility_field (pass (d,d) array or callable returning (d,d))"*. Measured: a callable tensor emits `UserWarning: Spatially-varying diffusion tensor averaged to constant per-axis weights` and nothing naming the callable. The test now asserts that text, plus that no warning names the callable — so reinstating the old substring fails instead of passing.
  - **`three_mode_api_migration_guide.md` contrasted a class with itself.** It told users the factory pairs with `FPSLAdjointSolver` (forward splatting), *not* `FPSLSolver` (backward interpolation). `FPSLAdjointSolver` was renamed to `FPSLSolver` in v0.17.6, so the two sides of that contrast had been the same class for five minor versions. The real pair is `FPSLSolver` (forward SL) against `FPSLJacobianSolver` (backward SL with Jacobian correction), which `scheme_factory.py`'s `_create_sl_pair` states and implements.

- **One statement the removal cost, recorded rather than dropped** (Issue #2343). `FPSLAdjointSolver <- FPSLSolver` was the only case in the package of a solver inheriting a capability declaration from a *sibling* rather than from `BaseMFGSolver`. Two census tests turned on it. Both now assert the set is empty rather than deleting the check, so a solver that starts inheriting a capability from a non-base parent has to come back and decide whether the inherited value is the claim it means to make.
