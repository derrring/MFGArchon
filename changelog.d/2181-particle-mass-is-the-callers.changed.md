- **`FPParticleSolver`'s default `kde_normalization` becomes `NONE`, and `KDENormalization.INITIAL_ONLY` is removed** (Issue #2181). Callers who did not name the parameter inherit the default change silently, so it is recorded apart from the fix. **Why `ALL` is not the default:** since the same change measures every slice on `geometry.integrate`'s measure, `ALL` pins exactly what `SolverResult.mass_conservation_error` reports, and that diagnostic reads round-off for any completed solve — measured 2.220446e-16 to 6.661338e-16 across n = 11/21/41 and N = 500/2000/5000. Conservation by fiat is what #1683 removed from `fp_fdm`, `fp_gfdm` and `network_solvers/fp_network`; this solver was the campaign's surviving instance. The same fixtures now report a number that varies -- but **not** a measure of conservation: the reported error is blind to particle absorption and on one pair anti-correlated with it (99.6% of particles lost reports 4.7079e-02 against 4.9722e-02 for a solve that lost none). That is the solver's property, identical on `main`, tracked as #2188. The case for `NONE` is that it does not fabricate conservation, not that it measures it. `ALL` remains available and is documented as fiat. The companion `removed` entry records `KDENormalization.INITIAL_ONLY`'s deletion, which is breaking and belongs under that heading rather than this one. `ParticleConfig.normalization`'s `Literal` is narrowed to `["none", "all"]` and its default moved with it.
