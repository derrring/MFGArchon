- **`check_solver_duality` now flags a semi-Lagrangian pair of which one half sub-steps and the other does not (#2440).** It classified a pair by `_scheme_family` alone, so every `HJBSemiLagrangianSolver` + `FPSLSolver` pair was `DISCRETE_DUAL`. That included a hand-built pair with the HJB half's sub-stepping off and `FPSLSolver`'s default on, which converges in 60 sweeps before #1880's fix and not after (asymmetry 0.95 after 200), and #1880's own mismatch in the other direction. It now returns `NOT_DUAL` with a warning for such a pair, so Expert Mode says so.
  - Only the switch is compared. On #1880's fixture an FP half at `cfl_target` 0.45 or 1.5 is as stable as the matched pair. A `cfl_target` far above 1 is misjudged: a half at 50 behaves as if its sub-stepping were off (an FP half at 50 grew the asymmetry 3.308x per sweep, exactly as with it off), an FP half at 4 grew it 2.462x, and an HJB half at 1.5 is unstable on its own. No bound has been measured (#2448).
  - Not compared: an HJB half on the canonical-CS or DPP path, for which no oracle says which FP schedule pairs with it (#2441), and a half that declares no schedule.
  - `create_paired_solvers` builds matched pairs as before. Given an `fp_config` that undoes the match, it now raises naming the conflict, where it built the mismatched pair silently. It also stops writing its defaults into the caller's `hjb_config` / `fp_config`: a reused `fp_config` carried one HJB half's schedule into the next pair.
