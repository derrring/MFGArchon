- **The particle FP solver returned mass 1 whatever the caller handed in, contradicting the mass the library reports** (Issue #2181). `MFGProblem` publishes `problem.initial_mass` and no longer rescales the caller's density (#1887); the particle solver then returned a density integrating to 1 regardless, a factor of **3.33** on a deliberate 0.3-mass population. **The mechanism is not `kde_normalization`, and changing its default would have done nothing:** measured, `NONE` gives mass 1.0 as well, with `_should_normalize_density()` returning `False` on every call and `_normalize_density` never invoked. The mass is destroyed by the **particle representation itself** — `sample_from_density` draws N particles from the density's *shape*, a set of positions carries no scale, and the KDE reconstruction returns ≈1 by construction. The quantity was not rescaled but **absent**, and had to be reintroduced deliberately. It is now restored at **each reconstruction**, before the density reaches the drift callable, by one factor calibrated once per solve on the first KDE output and measured with `geometry.integrate` so the solver preserves the functional the library reports (#2145). **Not at the exit, and not per slice** — both were tried and both are wrong: scaling the returned history rests on the FP step being linear in `m`, which is false when the drift depends on the density (`drift_needs_density` defaults to `True`; measured 85–102% relative error against a reference driven by the density the caller actually specified), while recalibrating per slice is normalisation by another name and erases the reconstruction's own drift. The caller's own array, where a path writes it into `M[0]` directly, is passed through neither operation: it is not a KDE output, so calibrating on it yields exactly 1.0 and leaves the rest of the history at mass 1, and normalising it is the rescale #1887 removed reappearing one layer down. Multi-population shares now survive this solver: two populations built for 0.3 / 0.7 return 0.300000 / 0.700000 summing to 1.000000, where both previously read 1.0 and summed to 2.0. **What this does not change:** the three `kde_normalization` modes stop meaning "the mass is 1", but they remain indistinguishable on the default `reflection` reconstruction and on `cic` (max difference 2.2e-16 and 5.6e-16 — both already conserve, so there is nothing to correct); only `standard`, which carries boundary bias, separates them (4.3e-02). And `ALL` pins `sum(M)*dx`, the rectangle rule, not the grid's measure, so `geometry.integrate(M[t])` still drifts — #2145's defect surviving inside this solver, tracked separately. Seven test assertions pinned the representation's loss and now assert drift from the initial mass or compare against the input; two absolute bounds on a density were rescaled by the caller's mass, one of them in an `optional_torch` file that every marker set deselects.
