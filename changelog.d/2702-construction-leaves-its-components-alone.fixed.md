- **Constructing a problem no longer changes the `MFGComponents` it was given** (#2702). `MFGProblem` and `NetworkMFGProblem` hold their own copy of the components and write into that.
  - **Before,** a soft wall (`state_penalty=`) was composed into the caller's object. A second problem built from the same components carried two walls, and the first problem then read the second wall too. A copy of a walled, Hamiltonian-defined problem's `problem.components` carried the composed wall into any problem built from it: one wall where none was asked for, two where one was. A second `NetworkMFGProblem` built from the same `NetworkMFGComponents` replaced the first problem's Hamiltonian with one on its own network.
  - **The public field changes** (user ruling, 2026-11-12): after a walled construction, `problem.components.hamiltonian` is the Hamiltonian as given, and the composed one is read through `problem.hamiltonian_class`.
  - **Rebinding a field of your own `MFGComponents` after the problem is built no longer reaches the problem.** The objects the fields hold (the Hamiltonian, `parameters`, the boundary conditions) are still shared. For `boundary_conditions` and a network problem's node functions, which the problem reads after it is built, rebind them on `problem.components`.
